# フェーズトライアル自動化プロンプト

> **本ファイルの内容は参照資料ではなく実行指示である。これを受け取ったら、
> 指定されたフェーズのトライアルに直ちに着手すること。**着手前に
> ユーザーへ確認・質問を返してはならない（ヘッドレス実行のため応答は返らず、
> 待つことはそのままセッションの終了を意味する）。判断を仰ぐべき事項は
> 手を止めるのではなく `patches/issue-*.md` に申し送る。
>
> **ターンを終える前に、自分の最後の段落を確認すること。** それが計画・分析・
> これからやることの宣言（「〜します」「次に〜へ進みます」）であって、**その作業の
> ツール呼び出しが伴っていないなら、今それを実行してからターンを終える**。宣言だけで
> 終えた時点でセッションが終了し、作業は再開されない（2026-08-06 のトライアルで発生。
> 文脈 128K・圧縮なしで、資源の制約ではなかった）。ターンを終えてよいのは、実行対象
> フェーズをすべて完了したときか、ユーザーにしか解けない事情で進めないときだけ。

**起動は `bin/run-trial.sh <最初のフェーズ> <最後のフェーズ>`**（リポジトリルートで実行）。
ランナーがフェーズごとに別セッションで `claude -p` を起動し、末尾へ
「この実行での対象は Phase N のみとする」を付ける。**したがって本ファイルを受け取った
セッションが担当するのは、原則としてそこで指定された 1 フェーズだけ**である。
末尾に指定が無い場合（手で `claude -p "$(cat prompts/trial-phase.md)"` を叩いた場合など）の
既定は **Phase 1 のみ**。複数フェーズを渡された場合は番号順に「共通の進め方」を繰り返す
（フェーズ間でリセットは掛け直さない）。

やることは、対象フェーズの実行 → 問題点の洗い出し → ドキュメント修正 → コミット。

## 前提条件

実行前に以下が満たされていることを確認する。満たされていない場合は作業を進めず、
その旨を報告して終了する。**報告の最終行には
`[phase-result] phase=<N> status=aborted reason=<短い理由>` を置く**
（後述「フェーズの結末マーカー」）。

> **前提条件 1・2 は、今回のフェーズが Phase 1 かどうかで分岐する。** ランナーは
> フェーズごとに別セッションで起動するため、Phase 2 以降のセッションでは
> **前フェーズの生成物と DB が残っているのが正常**であり、それを「リセット漏れ」と
> 判定して中断してはならない。

1. **`my-laravel-app/` の状態が、今回のフェーズと整合すること**。
   **このセッションからは `bin/reset-phase.sh` を実行しない**（破壊的操作のため。
   詳細は「共通の進め方」手順 1）。

   | 今回のフェーズ | 期待する状態 | 満たさない場合 |
   |---|---|---|
   | **Phase 1** | `my-laravel-app/vendor/` も `app/Models/` も**無い**（テンプレート状態） | リセット漏れ。`bin/reset-phase.sh 1` を **DB 破棄あり（`y`）** で実行してもらう |
   | **Phase 2 以降** | `vendor/` と `app/Models/` が**ある**（前フェーズを完走済み） | Phase 1 から実行されていない。実行順を確認してもらう |

   どちらも満たさない場合は作業を進めず、**どちらの期待に対してどう違ったか**を
   報告して終了する。

2. **Docker daemon が起動していること**: `docker info` で接続確認できること。
   未起動の場合は Docker Desktop を起動してもらう。

   **あわせて DB ボリュームの状態を確認する。**

   ```sh
   docker volume ls --filter name=my-laravel-app_db-data --quiet
   ```

   | 今回のフェーズ | 期待する出力 | 満たさない場合 |
   |---|---|---|
   | **Phase 1** | **0 行**（ボリューム無し） | 下記の理由により中断。`bin/reset-phase.sh 1` を **DB 破棄あり（`y`）** で実行し直してもらう |
   | **Phase 2 以降** | **1 行**（前フェーズが作ったものが残っている） | Phase 1 の `composer run setup` が走っていない。実行順を確認してもらう |

   > **Phase 1 開始時にボリュームが残っていると、旧スキーマの上にフェーズを積むことになる。**
   > `migrations` テーブルが残るため `migrate` は「Nothing to migrate」で素通りし、
   > 旧 `books` / `lendings` が残ったまま Phase 2 の新しいマイグレーションが走って
   > `CREATE TABLE` が「既に存在する」で落ちる。正しくリセットされていれば
   > `bin/reset-phase.sh` の DB 破棄確認（`y`）で `docker compose down -v` が消し、
   > Phase 1 の `composer run setup` が作り直す。
3. **実行セッションに許可リストが効いていること**: 本プロンプトはリポジトリ
   ルートで `claude -p` 起動されるため、適用されるのは**ルートの**
   `.claude/settings.json` のみ。`my-laravel-app/.claude/settings.json` は
   ルート起動のセッションには適用されない。フェーズ実行に必要な許可
   （`php artisan *`, `composer *`, `docker compose *`,
   `Edit`, `Write` 等）はルート側の許可リストに含めておくこと。
   なお **インタプリタにコードを直接渡す形は許可リストへ含めていない**
   （`php -r '<code>'` / `python3 -c '<code>'` / `node -e '<code>'` / `bash -c '<code>'` など。
   いずれも同じ理由）。**今後も追加しない。** composer.json 等のファイル内容の確認や
   集計は `grep` / `cat` / `jq` で行うこと（ワンライナーを書きたくなった時点で、
   だいたい `grep` で足りる）。

   > **ただしこの除外を「任意コード実行を防ぐ対策」と考えないこと。** 許可リストには
   > 同等の経路が複数開いており、**deny の強制力は「Claude Code が意図的に迂回しよう
   > としない」ことに依存している**（迂回経路の内訳と、設計を見直す場合の論点は
   > ルート `README.md` の「許可リストの設計前提」節）。
4. **手順書は Read して実行する**: ルート起動のセッションには
   `my-laravel-app/.claude/commands/` のスラッシュコマンドが読み込まれない
   場合があるため、**`/scaffold-phaseN-xxx` を試さず、対象のコマンドファイル
   （`my-laravel-app/.claude/commands/scaffold-phaseN-xxx.md`）を Read して
   その手順を直接実行する**（読み込まれていても中身は同じものが文脈に入るため、
   試して失敗する分の往復が減るだけ）。
5. **センシティブファイル保護の制約を織り込むこと**: Claude Code の
   センシティブファイル保護により、ヘッドレスセッションでは `.npmrc` および
   `.claude/` 配下のファイルへの書き込み・移動・削除が承認できず失敗する
   （許可リストの `Edit` / `Write` 許可よりも優先される）。この制約により:
   - Phase 1 の `.npmrc` はテンプレート同梱・git 追跡ファイルに格上げ済み。
     手順書は `rsync --exclude=/.npmrc` で生成物側の `.npmrc` を
     そもそも持ち込まないため、保護に抵触せず処理が止まらない。
   - 手順書（`my-laravel-app/.claude/commands/*.md`）の修正はヘッドレスでは
     行えない。**修正内容だけ**を `patches/edit-*.md` に書いてユーザーの適用を待つ
     （書式は `prompts/patch-format.md`。適用は対話セッションが行う）。
     元ファイルは Read で読める（**`cp .claude/commands/x.md patches/x.md` のように
     保護対象を「コピー元」に指定する形は拒否される**ので、コピーは使わない）。

     > **フル版を書き起こさないこと。** 過去のトライアルでは、3 ファイルの
     > フル版に 44,681 出力トークン（そのランの全出力の 23%）を使ったが、実際に
     > 変わったのは 1,424 行中 131 行——**全体の 9%** だった。残りは変わっていない
     > 部分を書き写すためだけの出力で、しかもそれが以降の全 API 呼び出しで
     > 文脈として課金され続ける。
   - **`.env` の Read は拒否されることも通ることもある。原因は未特定の揺れとして扱い、
     どちらの挙動も前提にしないこと**（Phase 3 の `.env.dusk.local` 作成時に拒否を、
     2026-08-05 と 08-06 のトライアルで成功を観測している）。手順書は
     `cp .env .env.dusk.local` してからコピー先を編集する形になっており、`.env` の
     全文 Read を必要としない。**新しい手順を書くときも `.env` の内容を読むことに
     依存させない。** 値の一次情報はテンプレート同梱の 2 ファイルだが、
     **置き場所が異なる**: リポジトリルート直下の `env.example`（ドット無し）と、
     `my-laravel-app/.env.example`（ドットあり）。`my-laravel-app/` をカレントにして
     `env.example` を読もうとすると存在せず失敗する（2026-08-06 のトライアルで踏んだ）。
   - 一方、**本ファイル（`prompts/trial-phase.md`）は `.claude/` の外にあり
     ヘッドレスからも直接修正できる**。トライアル中に判明した前提条件の誤り・
     手順の不足は、`patches/` を経由せずその場で
     反映してよい。`my-laravel-app/docs/*.md`・`my-laravel-app/CLAUDE.md`・
     `team-rules/*.md` も同様に直接修正できる。
6. **Bash ツールのコマンド形式の制約を織り込むこと**: 許可リストとは別に、
   Bash ツール自身が次の形のコマンドを拒否する。手順書にこれらの形を書くと
   ヘッドレスで実行不能になるため、代替形を使う:

   > **前提として、Bash ツールの作業ディレクトリは呼び出しをまたいで持続する。**
   > 一度 `cd my-laravel-app` すれば、以降の呼び出しはすべてそこがカレントになる。
   > **相対パスを書く前に今どこにいるかを疑い、確信が持てなければ `pwd` を打つこと。**
   >
   > この取り違えは 2026-08-06〜08 のトライアルで **7 回**踏んでいる（うち 3 回は
   > この注意書きを追加した後）。`patches/` と `bin/` はルート側と `my-laravel-app/`
   > 側の両方に存在するため、**エラーにならず静かに間違える**場合がある。
   > 「気を付ける」では止まらないので、**各フェーズ手順書の冒頭に「実行場所」の
   > 不変条件**を置いてある。フェーズに着手したら最初にこれを読み、
   > `cd my-laravel-app` を一度だけ行うこと。
   >
   > ただし**このトライアルのセッション自体はルートも触る**（`patches/` の読み書き、
   > 後述の `bin/phase-tokens.sh`）。不変条件が効くのは手順書の中だけなので、
   > ルート側の作業から手順書へ戻るときは移動し直す必要がある。
   - **シェル変数の展開を含むコマンド**（`Contains simple_expansion`）。
     `for i in $(seq 1 30); do ... done` のような待機ループは書けない。
     スクリプトファイル内に書くか、`docker compose up -d --wait` や
     `curl --retry` のようにコマンド側の機能で吸収する
   - **書き込み系コマンドの glob**（`Glob patterns are not allowed in write
     operations.`）。`mv src/* dst/` は不可。`rsync -a src/ dst/` を使う
   - **`find` の `-exec`**（`Bash(find:*)` では自動許可されない）。
     ファイルを変更する用途に `find` を使わない
   - **`sed -i` によるインプレース置換**。作業ディレクトリ内のファイルであっても
     `sed in '<path>' was blocked. For security, Claude Code may only edit files in
     the allowed working directories for this session` で拒否される。複数ファイルの
     一括置換は `Edit` ツール（同一ファイル内の複数箇所は `replace_all`）で行う
   - **`rm` によるファイル削除**。`sed -i` と同じく、削除対象が作業ディレクトリ配下に
     あっても `rm in '<path>' was blocked. For security, Claude Code may only remove
     files from the allowed working directories for this session` で拒否される
     （`my-laravel-app/storage/` 配下の一時ファイルで観測）。未追跡ファイルの削除は
     `git clean -fdxq <path>` を使う（同じファイルに対して通る）
   - **`git -C <path> ...`**（`Bash(git add *)` 等の前置パターンに一致しない）。
     git はセッションのカレントディレクトリからそのまま実行し、対象は相対パスの
     pathspec で絞る。**pathspec はカレントで書き分けが要る**ので、下表のどちらに
     いるかを確かめてから書くこと。

     > **`cd <path> && <コマンド>` の形は使わないこと。** `git` との組み合わせは
     > 「移動先のフックを実行しうる形」としてツールに拒否されるが、**それ以外の
     > コマンドとの組み合わせは通ってしまい、永続シェルのカレントが移動したまま残る**。
     > 移動に気づかないまま相対パスで続けると、`rm` の拒否・`git clean` の空振り・
     > `vendor/bin/...` の not found が連鎖する。カレントを変える必要があるときは
     > `cd` を単独のコマンドとして実行し、直後に `pwd` で確かめること。

     | カレント | 同じ対象を指す pathspec |
     |---|---|
     | `my-laravel-app/` | `git status --short -- docs ../prompts` |
     | リポジトリルート | `git status --short -- my-laravel-app/docs prompts` |

     > **ルートで `../prompts` と書くとリポジトリの外を指してエラーになる**
     > （`fatal: '../prompts' is outside repository at '<ルート>'`）。上の表の
     > 左列だけを見て形をコピーすると踏む。Phase 2 のトライアルで実際に起きた。

     > **pathspec を間違えても `git status` は黙って空を返す。** カレントが
     > `my-laravel-app/` のときに `git status --short -- my-laravel-app` と書くと
     > `my-laravel-app/my-laravel-app` を指すことになり、エラーではなく**出力 0 行**に
     > なる。「差分なし＝正常」と見分けが付かないため、生成物が並ぶはずの場面で空が
     > 返ったら pathspec を疑うこと（Phase 1 のトライアルで踏んだ）。カレント配下を
     > 丸ごと見るなら `git status --short -- .` と書く。
     >
     > **`git clean` も同じ pathspec を取るが、こちらは警告が出る。** 手順書の
     > `git clean -fdxq tmp-skeleton` を `my-laravel-app/tmp-skeleton` と書き換えると
     > `warning: could not open directory 'my-laravel-app/my-laravel-app/'` が返って
     > 何も削除されない（`git status` と違って気付ける）。
   - **`git status --cached` というオプションは存在しない**（`error: unknown option 'cached'`）。
     承認を求められるのは、存在しないオプションを含む形が読み取り専用コマンドとしての
     自動承認から外れるため。**許可リストに足しても解決しない**（コマンド自体がエラーになる）。
     staged の内容だけを見たいときは `git diff --cached --name-only` を使う
   - **`git -c <key>=<value> ...`**（サブコマンドの前に設定オプションを挟む形）。
     `git status` / `git log` / `git diff` が承認なしで通るのは許可リストではなく
     **Claude Code が読み取り専用コマンドとして自動承認しているため**で、`-c` を
     前置するとこの判定が効かなくなり承認待ちになる（例:
     `git -c core.quotepath=false status --short` が拒否された）。オプション無しの
     素の形で呼ぶこと。

     > **この形を許可リストへ足さないこと。** deny リストは `Bash(git push*)` の
     > ような前置パターンなので、`git -c foo=bar push` は一致せず**deny を迂回できて
     > しまう**。加えて `-c core.pager=...` / `-c alias.x=!cmd` は任意コマンド実行の
     > 経路にもなる。
   - **出力リダイレクト**（`> foo.log`）。**作業ディレクトリの内側を指す場合も拒否される。**
     バックグラウンド実行はツールの `run_in_background` を使う

     > **エラーメッセージに騙されないこと。** 拒否文は `Claude Code may only write to
     > files in the allowed working directories for this session: '<リポジトリルート>'`
     > と出るので**ルート配下を指せば通ると読めるが、通らない**（Phase 3 のトライアルで
     > `> /tmp/coverage_output.json` と `> coverage_output.json` の両方が同一文面で拒否された）。
     >
     > **回避はリダイレクトを使わないこと。** 標準出力はツールの結果としてそのまま読める。
     > 終了コードで合否を判定するもの（`vendor/bin/pest --coverage --min=80` 等）は、
     > 非 0 なら Bash ツール自身がエラーとして返すため、それで判定できる。トライアルでは
     > `vendor/bin/pest --coverage --min=80; echo "EXIT_CODE=$?"` の形も通っている
     > （下の `;` の項は「常に止まる」ではなく「止まりうる」と読むこと）。
     > **なお対話セッションでは再現しない**ので、**手順書に「ログをファイルへ落とす」形の
     > 指示を書かないこと。**
   - **`&&` / `||` / `;` で複数コマンドを繋いだ形**。「複数操作を含む」として
     承認を求められ、ヘッドレスでは止まる。1 コマンド 1 呼び出しに分け、
     並列に投げてよいものは同一ブロックで複数呼び出しにする（`cd` も
     単独のコマンドとして実行する）
7. **破壊的コマンドの deny リストを織り込むこと**: `rm -rf *`, `git push*`,
   `git reset --hard*`, `php artisan migrate:fresh*`, `php artisan db:wipe*` は
   `.claude/settings.json` の deny リスト（ルート CLAUDE.md 厳守事項 #2 に対応）で
   拒否される。ヘッドレスでは確認応答ができないため、これらに依存する手順は
   実行不能になる。代替: 未追跡ファイルの削除は `git clean -fdxq <path>`、
   DB の再構築は `docker compose down -v` → `composer run setup`。
   手順書にこれらの破壊的コマンドを書かないこと（見つけたら代替形へ修正する）。

## 呼び出し回数を抑える

Claude API はステートレスで、**1 回の呼び出しごとに会話履歴を丸ごと送り直す**。
したがってコストは「何をしたか」より「**何回リクエストしたか**」で決まる。

入力の 97.8% は cache 読取（＝再送分）である。したがって**コストを決めるのは
「1 呼び出しあたり何個のツールを使ったか」（密度）**で、同じ仕事でも束ね方だけで倍以上変わる。
同じ Phase 2 を 2 回実行した実測:

| 密度 | 呼び出し | ツール使用 | 合計トークン |
|---:|---:|---:|---:|
| **2.60** | 35 | 91 | **3.9M** |
| **1.83** | 60 | 110 | **7.0M** |

**仕事量はほぼ同じ（ツール 91 対 110）で、違いは束ね方だけ。** 密度 1.00（＝毎回 1 個ずつ）
まで落ちたランもあり、そこでは同じ作業が 3 倍以上に膨らんでいる。**以下は努力目標ではなく
守る規則とする。密度は `bin/phase-tokens.sh` が毎回出すので、報告の表で自分の値を確認できる。**

### まとめる

**次の操作の内容が、前の操作の結果に依存しないなら、同じブロックで同時に呼ぶ。**

- 複数ファイルの Read（`docs/db-schema.md` と `docs/screens.md` を続けて読む等）
- **異なるファイル**への Edit / Write
- 互いに独立した読み取り専用の Bash（`git status` と `ls` と `grep` 等）

> **実測で最も多い違反が 2 番目である。** Phase 2 は 7 モデル分のマイグレーション・モデル・
> ファクトリを作るが、これを 1 ファイルずつ Edit したランは単独 Edit が 12 回に達し、
> 束ねたラン（同 1 回）に対して**呼び出しが 27 回増えた**。生成するファイルの内容が
> それぞれ独立に決まるなら、**何個あっても 1 呼び出しにまとめる**。
>
> 「1 個ずつのほうが確実」という判断は誤りである。Edit / Write は失敗すればその
> ツールだけがエラーを返すので、まとめても切り分けは失われない。

### まとめない

以下は順序か因果が結果を変えるため、必ず分けて呼ぶ。

- **同一ファイルへの複数 Edit**（競合する。同一ファイル内の複数箇所は `replace_all` を使う）
- **順序が結果に影響するコマンド**。特に `php artisan make:model` は生成順が
  マイグレーションのタイムスタンプ順＝実行順になるため、**並列化すると FK 依存が壊れる**
  （`scaffold-phase2-models.md` の「生成の順序を FK 依存に合わせること」参照）
- **前の結果を見てから内容を決める操作**（テストの失敗を読んでから直す等）

### スクリプトへ寄せる

Bash ツールは `&&` / `||` / `;` の連結を拒否するため（前提条件 6）、手順書に
コマンドの列を書くと**その数だけ往復が発生する**。ただしこれはツールの制約であって
シェルの制約ではない。**スクリプトファイルの中身には適用されない。**

決まった手順の繰り返しは、既存のスクリプトを使うか、新しく作って 1 回にまとめる。

| スクリプト | 実行する場所（カレント） | 代替する検査 |
|---|---|---|
| `bin/doctor.sh` | `my-laravel-app/` | 環境の前提条件（PHP / 拡張 / Composer / Node / Docker / ポート） |
| `bin/check-repo.sh` | `my-laravel-app/` | `.env` の整合・生成物の `.gitignore` 除外・テンプレート同梱ファイルの変更 |
| `bin/phase-tokens.sh` | リポジトリルート | フェーズごとのトークン消費の集計 |

> **スクリプトは `bash` を付けず直接実行する**（`bin/check-repo.sh`）。実行ビットは
> `100755` でコミット済みなので `bash bin/check-repo.sh` と書く必要はない。許可リストは
> どちらの形も通すようにしてあるが、直接実行の形に揃えておくこと。
>
> **`bin/` はリポジトリルートと `my-laravel-app/` の両方にあり、中身は別物。**
> 上表の 2 つはルートには無いので、ルートから `bin/check-repo.sh` と打つと
> `exit 127` になる（トライアルで実際に踏んだ）。逆に `bin/phase-tokens.sh` /
> `bin/reset-phase.sh` / `bin/run-trial.sh` はルートにしか無い。
> **スクリプトを呼ぶ前に、その置き場と今のカレントが一致しているか確かめること。**

> **束ねた結果、どれが落ちたか分からなくなってはいけない。** 新しく作る場合も
> 上記 2 つと同じく、**項目ごとに `[OK]` / `[NG]` と対処を出す**こと。
> トライアルの目的は手順書のどこが壊れているかの特定であり、それを潰しては本末転倒になる。

## 実行モデル

**実際に動いているモデルによって、このセッションが持つ修正の権限が変わる。**
判定は**モデル名**で行う（システムプロンプトが示す名前）。

| 動いているモデル | 位置づけ | その場修正 |
|---|---|---|
| Opus 系 / Fable 系 | 既定 | 「共通の進め方」手順 4 のとおり |
| **Sonnet 系 / Haiku 系** | **実行と記録に専念** | 明白な誤字脱字のみ |
| 判別できない | **同上（記録に専念）** | 同上 |

> **`--model` フラグの有無で判定しないこと。セッション内から起動フラグは判別できない。**
> 2026-08-06 の Phase 1〜3 トライアルは `--model sonnet` で起動されたのに、
> 「`--model` 指定の有無が判別できない」として制限のない側の規則を適用し、
> **4 時間 44 分・6,600 万トークンを消費した Phase 3 の観測記録が残らなかった**。
> 起動フラグは分からなくても、**自分がどのモデルかは分かる**。そちらで判定する。
>
> **判別できない場合は制限する側に倒す。** 誤って制限した場合の損失は
> `patches/` の申し送りが数件増えることだけだが、誤って制限を外した場合は
> 誤った自動修正がテンプレートへ入り、しかもコミットとして正常な差分に見える。

**セッションは自分のモデル名と、適用した規則を報告の冒頭に書く。**
一次情報はトランスクリプトの `message.model` で、後から `bin/phase-tokens.sh` が読む場所と同じ。

### Sonnet 系 / Haiku 系（判別できない場合もここ）

**目的が違う。** このモードは手順書を直すために走らせるのではなく、**手順書のどこで詰まるか、
どこを自分の判断で埋めたかを記録するため**に走らせる。判定は後日、対話セッション（Opus）が
トランスクリプトと `patches/` を突き合わせて行う。

記録そのものは「共通の進め方」手順 3 でどのモデルでも要求される。ここで変えるのは
**権限**と、**分類を行わないこと**の 3 点だけ。

1. **その場で直すのは、明白な誤字脱字・リンク切れ・コマンドのタイプミスに限る。**
   手順 4 の「その場で直す」（修正が一意に定まるもの）と「その場で削る・圧縮する」は
   **適用しない**。判断を伴うものは、たとえ直し方が一つに見えても `patches/` へ回す。

   > 誤った自動修正はコミットとして正常な差分に見えるため、**後段の判定を素通りする**。
   > 「後で Opus が判定する」という前提そのものが、この経路では機能しない。

2. **`team-rules/*.md` は一切変更しない**（既定でも申し送り対象だが、ここでは例外なく禁止）。

3. **記録は「共通の進め方」手順 3 のとおり**（詰まった箇所・解釈・自分で埋めた箇所を
   `patches/issue-*.md` に残す）。このモードではそれに加えて、**分類しない。** 「手順書の欠陥」「誤読を招く書き方」「モデル能力の限界」
   「テンプレートの道具の不具合」の切り分けは**行わず、観測したことだけを書く**
   （分類の定義は README の「issue の切り分け（対話セッション向け）」の表。ヘッドレスからは読まなくてよい）。切り分けには手順書の意図と
   他モデルでの再現性が要り、実行中のセッションには両方とも無い。issue ファイルの
   `状態:` は `未分類` とし、「選択肢」「推奨」節は
   `未記入（判定は対話セッションで行う）` と書いてよい。

   **推測を書く場合は観測と混ぜない。** 原因に心当たりがあっても、`根拠` 節には
   再現できる事実だけを置き、推測は「未特定」と明示したうえで可能性として並べる
   （2026-08-06 の Phase 1 トライアルはこの書き分けができていた。推測した原因は
   外れていたが、断定していなかったため後段の調査を誤らせなかった）。

## 共通の進め方

今回のフェーズについて、この手順を順に適用する。

1. **リセット（`bin/reset-phase.sh`）はこのセッションでは実行しない。** **起動前に
   ユーザーが `bin/reset-phase.sh <フェーズ番号>` を実行済み**であることを前提とする
   （前提条件参照）。`reset-phase.sh` は `docker compose down -v` / `git clean` /
   `git checkout` を伴う破壊的操作であり、ヘッドレスで確認応答なしに走らせるべきでは
   ないため、**セッション側から呼ばないこと**（複数フェーズを担当する場合も、
   フェーズ間で掛け直さない。テンプレート状態まで巻き戻る仕様のため、掛けると
   Phase 1 からの再実行が必要になる）。
2. **トークン計測の開始マーカーを出力する**（後述「フェーズごとのトークン計測」）。
   そのうえで `my-laravel-app/` ディレクトリに移動し、対象の手順書
   （`.claude/commands/scaffold-phaseN-xxx.md`）を Read して実行する（前提条件 4）
3. 実行中に発生したエラー・警告・非対応バージョン等の問題を記録する。次の 3 つは
   **フェーズが成功していても** `patches/issue-*.md` に残す（モデルを問わず必須）。

   - **詰まった箇所**: 手順書のどのステップで、何を試して、何が起きたか。エラー出力は原文のまま
   - **手順書をどう解釈したか**: 記述が一通りに読めなかった箇所は、**自分がどちらの意味に
     取ったか**を書く
   - **自分の判断で埋めた箇所**: 手順書に書かれておらず自分で決めたこと（ファイル名・値・順序など）

   > **自力で回復できたものも記録する。回復できたかどうかで判断しない。** 自分のミスに
   > よる失敗（実行順の誤り・パスの取り違え・自作クエリの誤り・Read せずに Write を試みる等）
   > も含める。**測っているのは「何が読み手を詰まらせうるか」であって、回復の速さではない。**
   >
   > **手順書・`docs/` が「正常」「想定どおり」と明記している事象は、issue ファイルを
   > 作らず報告の「自力で回復した失敗」欄に挙げるだけでよい。**ただし除外できるのは、
   > **その記述の箇所を `ファイル:行` で示せたものだけ**で、示せないものは除外しない
   > （「既知のはず」という自己判断で握り潰す経路を残さないため）。例:
   > `scaffold-phase1-skeleton.md:411`（停止まわりの `pkill` / `concurrently` の
   > 終了コード 1）。
4. 見つかった問題はまず根本原因を特定する。そのうえで、**その場で直すもの**と
   **判断を仰ぐもの**に振り分ける。

   > **`--model sonnet` で起動されている場合、この手順のうち「その場で直す」と
   > 「その場で削る・圧縮する」は適用しない。**「実行モデル」節の規則が優先し、
   > 判断を伴うものはすべて `patches/` へ回す。

   **その場で直す**（修正が一意に定まるもの）: 原因が手順書・docs の記述の
   誤りに特定でき、テンプレート内で完結し、妥当な直し方が 1 つしかないもの。
   `my-laravel-app/.claude/commands/scaffold-phaseN-xxx.md`、
   `my-laravel-app/docs/*.md`、`my-laravel-app/CLAUDE.md`、`team-rules/*.md`
   を修正する（`.claude/` 配下は前提条件 5 のとおり `patches/` 経由）。

   **その場で削る・圧縮する**（記述が不要になったことを確定できるもの）: 手順書と docs には
   過去に踏んだ罠の記録が積み上がる一方で、減る契機がない。実行して**もう再現しなかった**
   記述に気づいたら、次のとおり扱う。

   - **削ってよい**のは、次を**すべて**満たすものだけ:
     - 事象が特定バージョンで解消済みだと記述自体に書かれている
     - テンプレートがそのバージョン以降を前提にできる（依存の下限が保証されている）
     - 削っても切り分けの手順が失われない（版の確認方法などが別の場所に残る）
   - 満たさないものは**削らず圧縮する**。内部実装の解説を落とし、「何を確認して
     どう分岐するか」だけ残す。**一次情報を `docs/` に置き、手順書からは参照にする**
   - 判断がつかないものは触らず `patches/issue-*.md` に申し送る

   **追記より削除のほうが危険である。** 「もう起きない」と判断して消した罠が、条件付きで
   再発することがある。迷ったら残す側に倒すこと。

   **`patches/issue-*.md` に申し送る**（次のいずれかに当たるもの）:
   - 妥当な解が複数あり、どれを採るかが**方針の選択**になる
     （パッケージの選定、バージョンの下限、ディレクトリ構成の変更など）
   - `team-rules/*.md` の**ルールの中身**を変える必要がある。ここは利用者の
     本番プロジェクトに配布されるため、ヘッドレスの単独判断で書き換えない
   - 再現条件が不確か、または 1 回しか観測できておらず、原因の特定に
     至っていない
   - 権限拒否・ツール制約により**検証しきれなかった**（回避策は動いたが、
     手順書に書くべき形かどうかの確証がない）
   - テンプレートのスコープを超える（Docker イメージ、ホスト環境、
     Laravel 本体の挙動など、こちらで直せないもの）

   **フェーズが成功していても申し送るもの**。次の 4 つは実行が止まらないため
   問題として記録されずに消えるが、いずれも実行した本人にしか観測できない:
   - **権限拒否**: 拒否されたコマンドは**すべて**報告の「権限で拒否された
     コマンド」へ原文のまま列挙する。そのうえで、**対話実行（手動）ならユーザーが
     承認して先へ進められたか**で切り分け、前者だけ issue を作る。
     - **許可リストの不足**（対話なら承認でき、`.claude/settings.json` への追記で
       恒久的に解消する）→ `patches/issue-phase<N>-permission-denied.md` を
       **必ず作る**。反映先の設定はヘッドレスから書き込めず、報告本文は
       セッション終了後に追えなくなるため、ここに残さないと恒久化されない
     - **センシティブファイル保護・deny リスト**（対話でも承認できず、設定変更でも
       解消しない）→ **issue は作らない**。前提条件 5・7 に記述済みの既知事象で
       ある旨を報告へ 1 行添えるにとどめる。**ただし前提条件に書かれていない対象を
       新たに踏んだ場合は、前提条件そのものの更新が必要なので issue を作る**
   - **手順書は正しいが誤読した箇所**: 記述に誤りはないが、一度誤った解釈を
     して手戻りしたところ。誤りではないので「その場で直す」対象にならないが、
     放置すると他の利用者の Claude Code も同じ誤読をする。どう読み違えたかと、
     どう書かれていれば迷わなかったかを書く
   - **バージョン・環境の陳腐化**: 引いてきた依存のバージョンが
     手順書の想定と違う、非推奨警告が出た、`.tool-versions` の PHP / Node が
     実際の要求と乖離している等。動くので失敗にはならないが、時間経過で必ず
     顕在化する。追随するかどうかは方針判断
   - **フェーズ境界のズレ**: 本来別フェーズでやるべき作業が混ざっている、
     1 フェーズが長くコンテキストが切れかけた等。フェーズ設計の変更は
     影響範囲が広い

   迷った場合は申し送る。誤った自動修正がテンプレートに入る方が、
   未解決の申し送りが 1 件残るより高くつく。
5. `/verify` でそのフェーズの完了基準を満たしているかセルフチェックする
6. 満たしていなければ 3〜5 を繰り返す
7. 修正が完了したら、論理的な単位ごとに分けて **`main` ブランチへ直接
   コミットする**。**本プロンプトによる起動をもってコミットの明示的な指示と
   みなす**ため、提案に留めず実際にコミットすること。ブランチは切らない。

   > **コミット対象はテンプレートの修正（手順書・docs・`team-rules/`・本ファイル・
   > `bin/`）と `patches/` のみ。`my-laravel-app/` のフェーズ成果物（アプリ生成の
   > 生成物・モデル・マイグレーション等）は絶対にコミットしない**。成果物は
   > `bin/reset-phase.sh` の設計前提として git 管理外であり（同スクリプトの
   > 設計メモ参照）、コミットすると checkout がそれを復元してしまいリセットが
   > 機能しなくなる。「フェーズを完走させた」こと自体はコミットではなく
   > 報告で残す。
   このとき `team-rules/git-workflow.md` の次の 2 条項は**本トライアルには
   適用しない**（これ以外の条項には従う）:
   - 「ユーザーの明示的な指示なしに `git commit` しない」
   - 「フェーズ実行中は Claude Code 側からコミットの提案・実行を行わない」

   `git push` 禁止・ファイルの明示指定・メッセージ規約などの詳細はルート
   `CLAUDE.md` の「このリポジトリ自身の git 運用」に従う

   申し送りファイル（`patches/issue-*.md`）も同じくコミットに含める。
   テンプレートの修正とは**別コミット**に分ける
   （例: `docs(patches): Phase 3 で判断が必要な事項を申し送り`）。

   **マーカーはここでは出さない。`[phase-tokens] event=end` と `[phase-result]` は
   どちらも手順 8 の報告の末尾に置く**（後述「フェーズごとのトークン計測」
   「フェーズの結末マーカー」）。複数フェーズを担当している場合は、報告まで終えてから
   手順 1 へ戻る。
8. 結果を報告する（形式はルート `CLAUDE.md` のコミュニケーション節に従う）。

   > **報告は「最後のメッセージ」として単独で完結させること。報告の後に要約・締めの
   > 文を出さない。** `claude -p` は**最終メッセージだけを標準出力へ出す**ため、
   > 報告を書いた後に「上記が完了報告です」のような一文で締めると、**報告本文が
   > まるごと出力から失われる**（2026-08-06 の Phase 1〜2 トライアルで実際に起きた。
   > 34 文字の締め文だけが出力され、報告はトランスクリプトを掘らないと読めなかった）。
   >
   > **報告の最終行は `[phase-result]` マーカーにする**（「フェーズの結末マーカー」節）。
   > これも標準出力に乗せる必要があるため、報告の中に置く。マーカーの後には何も書かない。

   このセッションの内容は**別セッションのユーザー・Claude が読んで判断・適用する**
   ため、報告の末尾に次の各点を必ず添えること:

   - **実行モデル**: このセッションのモデル名（「実行モデル」節）。判別できなかった場合は
     その旨と、「指定なし」の規則を適用したことを書く。後段の判定がこの値を前提にするため、
     **報告の冒頭に置く**。
   - **セッション transcript のパス**: `~/.claude/projects/<エンコード済みパス>/<セッションID>.jsonl`。
     セッション ID はスクラッチパッドディレクトリのパスに含まれているので、そこから
     導出した値をそのまま報告する。**実在確認は不要**（作業ディレクトリ外のため
     `ls` が拒否される。必要ならユーザー側で `bin/watch-trial.sh` により行える）。
   - **権限で拒否されたコマンド**: **原文のまま**列挙する（許可リストへ反映するための
     一次情報なので要約・言い換えをしない）。1 件も無ければ「なし」と書く。
   - **手順どおりに実行できず迂回した箇所**: 別手段に切り替えた箇所と理由。
     手順書が権限や環境の制約で実行不能なケースは、成果物（コミット）にも
     報告の要約にも痕跡が残らず、後から発見できないため。
   - **自力で回復した失敗**: 手順 3 に従って記録したものを件数と概要で挙げる
     （詳細は `patches/issue-*.md`）。**「なし」と書けるのは、トランスクリプトに
     エラーで返ったツール結果が 1 件も無いときだけ**で、それ以外で「なし」と書くのは
     報告の不備として扱う。
   - **`patches/` に残したファイル**: `patches/edit-*.md`（適用が必要な修正）と
     `patches/issue-*.md`（判断が必要なもの）をパスとタイトルで列挙する。
     1 件も無ければ「なし」と書く。
   - **ユーザーが手で確認する必要が残っている項目**: ヘッドレスでは原理的に
     実施できない**完了基準**を列挙する。**1 件でも残っていればフェーズを「完了」と
     書かない。** 自動で埋まらない項目は報告に出さないと存在ごと忘れられるため、
     該当が無い場合も「なし」と明記する。なお Phase 5 手順 9 のブラウザ目視確認は
     完了基準から外した（任意の確認に格下げ）ため、ここには挙げない。
   - **今回参照しなかった注意書き**: 手順書・docs の注意書き（過去に踏んだ罠・
     既知事象）のうち、**この回で一度も参照せず、再現もしなかったもの**を箇所
     （ファイル:行）付きで列挙する。削るかどうかはここでは判断せず、「なぜ不要に
     見えたか」を 1 行添えるにとどめる（削除の可否は対話セッションで決める。
     手順 4 の削除基準をすべて満たすものだけは、その場で処理してよい）。
     該当が無ければ「なし」と明記する。
   - **導入されたバージョン**: `composer.lock` を一次情報として主要パッケージの
     版数を列挙する（`laravel/framework` / `laravel/breeze` / `livewire/livewire` /
     `livewire/volt` / `laravel/dusk` / `pestphp/pest` / `laravel/boost`）。
     記憶やコマンド出力の見た目で書かないこと。手順 4 の「バージョン・環境の
     陳腐化」の申し送り判断がこの値に依存する。
   - **フェーズ別のトークン消費**: 報告を書く直前にリポジトリルートへ `cd` して
     `bin/phase-tokens.sh` を実行し、**出力された Markdown 表をそのまま貼る**
     （加工・要約しない）。集計対象は自動検出される最新のトライアルセッション、
     すなわちこのセッション自身。**この報告自体の消費は表に含まれない**ので、
     その旨を表の下に 1 行添える。権限で拒否された場合は表の代わりに
     「拒否されたため未計測」と書き、コマンドを上記の項目にも原文で挙げる
     （ユーザーが後から取得できるため、フェーズの失敗ではない）。

## フェーズごとのトークン計測

各フェーズがどれだけトークンを消費したかを後から集計できるよう、フェーズの
開始時と終了時に、**次の形の 1 行だけを本文として出力する**（ツール呼び出しでは
なく、通常のテキスト出力として）。

```
[phase-tokens] phase=<N> event=begin
[phase-tokens] phase=<N> event=end
```

- `begin` は「共通の進め方」手順 2 の冒頭（`my-laravel-app/` へ移動する前）、
  **`end` は手順 8 の報告の末尾、`[phase-result]` の直前**に出力する。手順 7（コミット
  直後）に置くと**報告を書くコストが丸ごと「マーカー外」に落ちる**。フェーズの実行だけ
  でなく、修正・`/verify`・コミット・報告までを 1 フェーズの消費として測る

  > **ただし報告に載せるトークン表は、その報告自身の消費を含められない**（表を作る
  > `bin/phase-tokens.sh` は `end` より前にしか置けないため）。表には「本報告作成直前
  > 時点まで」と添えること。**含められないのは表の数値だけで、`end` を報告末尾に置いて
  > おけば、後から実行し直した集計には報告分も入る。**
- 出力するのはこの 1 行のみ。前後に説明文を足さない。**この行を他の文脈で
  書かない**（引用・説明のために書くと、その位置で区間が切り替わってしまう）
- 実体は `bin/phase-tokens.sh` が読むマーカーである。トランスクリプト
  （`~/.claude/projects/.../<セッションID>.jsonl`）の assistant のテキストブロックを
  走査し、`begin` から `end` までの API 呼び出しの `usage` を合算する。マーカーを
  出し忘れた区間は「マーカー外」に落ちるだけで、実行そのものには影響しない

## フェーズの結末マーカー

**各フェーズの結末を、次の形の 1 行だけで出力する。**

```
[phase-result] phase=<N> status=ok
[phase-result] phase=<N> status=aborted reason=<短い理由>
```

**置く場所は「報告の最終行」。** 手順 8 の報告を書き終えた最後に、この 1 行だけを
足して終わる。行頭から始め、前後に説明文を付けない。

> **コミット直後（手順 7）に出してはならない。** `claude -p` は**最終メッセージだけを
> 標準出力へ出す**ため、報告より前に置くとログに残らず、ランナーの `grep` が空振りして
> **成功したフェーズで実行が止まる**（過去のトライアルで実際に発生。経緯は README の
> 「フェーズごとに別セッションで回す」節）。
>
> **`[phase-tokens] event=end` も報告の末尾（`[phase-result]` の直前）に置く**
> — 理由は前節参照。ランナーの `grep` は `^\[phase-result\]` だけを見るので影響しない。

- `ok` は**そのフェーズの完了基準をすべて満たした**とき
- `aborted` は前提条件を満たさず着手できなかったときと、完了基準を満たせないまま
  終わったとき。`reason=` は空白を含まない短い語（例: `reason=前提条件2`、
  `reason=dusk失敗`）
- **着手できなかった場合も、対象フェーズについて `aborted` を出力する**
  （この場合も報告の最終行に置く）

> **なぜ要るか。** 前提条件を満たさず「終了します」と報告した場合も CLI としては
> 成功（0）で終わるため、**ランナーは終了コードでは成否を判別できない**。この行を
> `grep` して次のフェーズへ進むかを決めている。

## 修正パッチの書式（`patches/edit-*.md`）

ヘッドレスから書き換えられない `.claude/` 配下のファイルへの修正は、**変更点だけ**を
`patches/edit-*.md` に置き、対話セッションが適用する。**書式は `prompts/patch-format.md`
に分けてある。`patches/edit-*.md` を書く必要が生じた時点でそれを Read し、従うこと**
（使わない回のほうが多いため、本ファイルには含めない）。

## 判断が必要な事項の申し送り（`patches/issue-*.md`）

ヘッドレスでは決められない事項は、次のセッションのユーザーと Claude Code が
**対話で解決できる形**にして `patches/` に残す。報告本文はセッションが終われば
追えなくなるため、リポジトリに残るファイルを一次情報とする。

### ファイル

- 1 件 1 ファイル。`patches/issue-phase<N>-<英小文字ハイフンの短い slug>.md`
  （例: `patches/issue-phase3-livewire-version-conflict.md`）。
  接頭辞で区別する（`issue-` = 判断待ち、`edit-` = 適用待ちの修正パッチ）
- **`patches/` はリポジトリルート直下のディレクトリ**。手順 2 で `my-laravel-app/`
  へ移動した後に相対パスで書くと `my-laravel-app/patches/` に誤配置されるため、
  置くときはリポジトリルートからのパスであることを確認する（`edit-*.md` も同様）
- 問題が複数フェーズに跨る場合は最初に観測したフェーズ番号を使う
- 解決したファイルは**対話セッション側で削除する**。ヘッドレス側は追記のみ行い、
  既存ファイルを消さない（未解決と判断された結果として残っている可能性があるため）
- 同じ問題を再観測した場合は新規作成せず、既存ファイルの「何が起きたか」節に
  日付付きで追記する

### 書式

`状態:` は `未解決`（判断待ち）か `未分類`（`--model sonnet` の観測記録。切り分けから行う）。
`実行モデル:` は観測したセッションのモデル名で、**再現性の判断に要る**ため必ず書く。

```markdown
# <一行で問題を言い切るタイトル>

- フェーズ: Phase 3
- 状態: 未解決
- 初回観測: 2026-07-19
- 実行モデル: claude-opus-5

## 何が起きたか

手順書のどのステップで、何をしたら、何が起きたか。

## 根拠

エラー出力・コマンド・ファイルの該当箇所を**原文のまま**引く。
要約・言い換えをしない（別セッションが再現を試みる一次情報になるため）。

（エラー出力の原文をコードブロックで）

- 関連ファイル: `my-laravel-app/.claude/commands/scaffold-phase3-ui.md:120`

## なぜ自動で直さなかったか

「共通の進め方」手順 4 の振り分け基準のどれに当たるかを 1 行で。

## 選択肢

1. **<案 A>** — 影響: … / 懸念: …
2. **<案 B>** — 影響: … / 懸念: …

## 推奨

案 A。理由を 1〜2 行。

## 決めてほしいこと

<ユーザーが Yes/No か択一で答えられる 1 つの問い>

## 暫定対応

トライアルを先に進めるために取った回避策があれば書く。無ければ「なし」。
**回避策をテンプレート本体に入れた場合は、その差分もここに明記する**
（決着後に取り消す必要があるため）。
```

## 各フェーズの実行

担当するフェーズだけを「共通の進め方」に従って実行・修正・コミットする。
**指定されていないフェーズには何も手を出さない。**

「リセット」列は**起動前にユーザーが実行する**コマンド（このセッションでは実行しない）。

手順書は `my-laravel-app/.claude/commands/` 配下にあり、**Read して実行する**
（前提条件 4）。完了確認は各フェーズとも `/verify`。

| フェーズ | 内容 | 起動前リセット（ユーザー実行） | 手順書 | 前提 |
|---|---|---|---|---|
| Phase 1 | スケルトン生成 | `bin/reset-phase.sh 1` | `scaffold-phase1-skeleton.md` | — |
| Phase 2 | DB スキーマ・モデル生成 | `bin/reset-phase.sh 2` | `scaffold-phase2-models.md` | Phase 1 が単体で完走すること |
| Phase 3 | UI 実装（Controller / View / Policy） | `bin/reset-phase.sh 3` | `scaffold-phase3-ui.md` | Phase 1〜2 が完走すること |
| Phase 4 | UI テスト（Feature / Dusk） | `bin/reset-phase.sh 4` | `scaffold-phase4-ui-tests.md` | Phase 1〜3 が完走すること |
| Phase 5 | 仕上げ | `bin/reset-phase.sh 5` | `scaffold-phase5-finalize.md` | Phase 1〜4 が完走すること |
