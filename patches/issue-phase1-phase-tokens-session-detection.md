## 何が起きたか

本トライアルは、ユーザーとの対話セッション内で `prompts/trial-phase.md` の全文がそのまま
ユーザーの最初のメッセージとして渡される形で開始された（`claude -p "$(cat ...)"` による
狭義のヘッドレス起動ではなく、対話セッションのトランスクリプト形式で記録されている）。

「共通の進め方」手順9の報告作成時に `bin/phase-tokens.sh`（引数無し = 自動検出）を実行したところ、
明らかに別のトライアル（`prompts/trial-phase.md` 本文中の「2026-08-05 のトライアル（Phase 1〜4）の
実測」の数値、API 呼び出し 281 回と完全一致）のトランスクリプトを拾って集計した。

一方、スクラッチパッドのタスク出力パスから導出した本セッションの ID
（`fceeb16e-5164-4aff-b62f-5a2a81930a02`）を明示指定して再実行すると、
`[phase-tokens]` マーカーに基づく正しい Phase 1 の区間（API 呼び出し 73 回、経過 0:07:31）が
得られた。またこの ID は `bin/phase-tokens.sh --list` の候補一覧にも**現れなかった**
（候補一覧は `is_trial()` フィルタを通過したセッションのみを列挙するため、このセッションは
フィルタで弾かれていることになる）。

## なぜ自動で直さなかったか

「実行モデル」節の規則により、このセッション（`claude-sonnet-5`）では判断を伴う修正を
その場で行わない。原因（対話セッション形式のトランスクリプトでは `head -5` 相当の範囲に
マーカーが収まらない構造になっているのか、別の要因か）の特定に踏み込んでおらず、
「手順書の欠陥」「誤読を招く書き方」「モデル能力の限界」のいずれにも当たらない
（`bin/*.sh` はスクリプトの実装問題であり、これらの分類軸自体が想定していない対象）。
加えてこの事象は「前提条件に書かれていない対象を新たに踏んだ」ケースに該当するため、
申し送りとして残す。

## 決めてほしいこと

最新のトライアルセッションを拾えるように修正するか。修正する場合、`is_trial()` の
判定範囲（`head -5`）を広げるべきか、判定方法自体を変える必要があるか。あるいは
「本スクリプトはヘッドレス（`claude -p`）専用であり対話セッションでの利用は対象外」と
割り切り、`prompts/trial-phase.md` 側に「対話セッションから実行した場合は必ずセッション
ID を明示指定すること」という注意書きを足すだけに留めるか。
